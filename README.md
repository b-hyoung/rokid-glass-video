# 글래스 영상 (Rokid Glasses용)

현재 앱 소스는 0.2.22 후보입니다. 연결·촬영·인식 설정은 웹에서 제어합니다.

## 페어링 후보 실행

`python tools/start_secure_local.py`로 별도 8791 포트의 페어링 환경을 연다. 처음에는 설정 키가 채워진 연결 페이지가 열리며 새 공간을 만들고 등록 사본을 가져올 수 있다. 안경 앱은 빌드에 지정된 서버에 자동 접속한다. 웹의 **안경 연결** 목록에서 안경을 선택하면 연결된다. 안경에는 설정 화면이나 주소·코드 입력이 없다. 연결 해제와 촬영·인식 설정은 웹에서 한다. 기본 촬영은 같은 Wi-Fi WebRTC이며 H.264·JPEG는 고급 전송 설정에 남아 있다.

현재 후보는 보호된 로컬 운용 환경이며 실물 장시간 검사와 정식 서명 확인을 마친 출시본은 아니다. 아래 8787 실행은 기존 호환 개발 모드다.

## 로컬 PC에서 실행

Windows에서는 프로젝트의 **start-local.cmd**를 실행하거나 `python tools/start_local.py`를 사용한다. 현재 웹 인식 엔진과 안경 통신 규격을 PC의 로컬 Worker에서 실행하므로 Cloudflare의 운영 요청 한도를 사용하지 않는다.

- 사진·녹화 테스트: `http://localhost:8787/local-check.html`. JPG·PNG·WebP 또는 영상을 선택하고 **테스트 시작**을 누른다. 모니터링 녹화는 **영역 선택**으로 카메라 부분만 지정할 수 있다. 물체 이름·영역·처리 시간·첫 인식 시간과 1.5초 조준 진행률을 표시하고 연결 영상을 PC에서 미리 재생한다.
- 안경 실시간 제어·이미지 등록: `http://localhost:8787/recognition`. PC의 Chrome은 localhost 주소로 접속한다. 안경 서버 주소는 같은 Wi-Fi에 있는 PC의 LAN 주소로 지정한다. 실제 주소와 ADB 명령은 `http://localhost:8787/local-setup.html`에 표시된다. 기존 앱의 서버 지정 기능을 사용하며 APK 재설치는 필요 없다.
- 파일 테스트는 별도 로컬 저장소·명령 채널을 사용하므로 안경 실시간 세션에 재생 명령을 보내지 않는다. 등록 목록 새로고침으로 현재 PC 등록 내용을 테스트 화면에 복사한다. 영상 파일은 브라우저에서 해석한다.
- 등록 사진·벡터와 보정값은 `runtime/local-state`에 저장돼 재시작해도 유지된다. 운영 Cloudflare 등록 데이터와는 별개다. 백업 JSON이 있으면 `python tools/start_local.py --targets <파일>`로 빈 로컬 저장소에 가져올 수 있다. 이미 로컬에 등록된 대상이 있으면 덮어쓰지 않는다. 현재 PC의 준비된 백업은 `runtime/local-targets-import.json`이다.
- 창을 닫거나 Ctrl+C로 서버를 중지한다. `--no-open`은 브라우저 자동 열기를 끄고, `--port 8790`처럼 다른 포트를 선택하면 포트별 별도 저장소를 쓴다. 실행 로그는 `runtime/local-server.log`에 남는다.

준비물: Node.js·Python·Chrome 및 `release.json`에 고정된 모델·추론 파일. 새 체크아웃에서는 복구 안내에 따라 파일을 준비한다. Wrangler가 없으면 실행기가 프로젝트의 lockfile로 `npm ci`를 실행한다. 최초 도구 설치에는 인터넷이 필요하며, 이후 인식과 데이터 저장은 PC에서 수행한다. 물체 탐지 정확도는 운영과 같은 엔진의 현재 한계를 그대로 반영한다.

관련 파일: `tools/start_local.py`, `wrangler.local.jsonc`, `tools/local-worker.mjs`.

## 0.2.14 · WebRTC 시험

안경 앱 0.2.14와 이 버전의 Worker가 필요하다. 같은 Wi-Fi에서 안경 한 대와 Chrome 탭 한 개를 사용한다. 촬영 방식에서 **WebRTC · 같은 Wi-Fi 시험**을 선택하고 30fps로 촬영을 시작한다. **동영상 · H.264**를 선택해 다시 시작하면 기존 중계로 비교할 수 있다.

WebRTC 영상은 안경에서 브라우저로 직접 흐른다. Worker의 `/cam/rtc`는 연결 설정만 전달하며, 촬영 명령과 웹 인식·HUD는 기존 경로를 쓴다. 이 모드에서는 별도 YUV 출력 없이 촬영하며 HUD는 웹이 찾은 위치를 표시한다. 직접 연결이 가능한 LAN을 대상으로 하며 TURN은 구성하지 않았다.

로컬 시험은 `python tools/start_local.py`로 열고, PC에서는 `http://localhost:8787/recognition`에 접속한다. 안경 앱에는 같은 Worker의 PC LAN 주소를 지정한다. 기존 설치에 덮어쓸 APK는 기존과 동일한 키로 서명해야 한다.

## 0.2.10 · 안경 내부 추적과 표시 확인

`build/glass-video-0.2.10.apk` (versionCode 12). 기존 앱과 같은 서명으로 빌드한다. 설치 후 Cloudflare 웹을 새로고침하고 촬영·인식을 시작한다.

- 버튼/터치패드 탭은 로딩 중이거나 재생 중인 영상을 **종료**한다. 준비 완료 콜백이나 늦게 온 자동 재생 명령으로 다시 켜지지 않도록 취소한다.
- 로딩부터 재생 종료까지 서버와 안경 양쪽에서 다른 대상의 자동 재생을 막는다. 종료 뒤 중앙을 비우고 새로 2.5초 조준한다. 명시적인 웹 수동 재생은 교체할 수 있다. 재생 토큰으로 이전 영상의 종료 알림을 구분한다.
- 대상의 정체는 기존 Chrome OpenCV ORB/LK가 판단한다. 프레임마다 최대 12개의 7×7 흑백 특징 조각을 함께 전송하고, 안경의 현재 YUV 화면에서 검증한 뒤 위치를 따라간다. 안경은 별도 OpenCV 라이브러리 대신 Java 패치 상관 비교·왕복 검사·강건한 유사 변환을 사용한다. 새 신경망 학습이나 3D 공간 고정 기능은 아니다.
- 안경 분석 출력은 180×320 이하, 최대 15Hz, 최대 4대상이다. 영상 인코더와 별도 스레드에서 최신 이미지만 처리하고 카메라 버퍼를 먼저 반환한다. 원본 영상은 요청한 30/40/60fps H.264 전송 경로를 유지한다. 지원 크기·프레임 제한을 확인하고 YUV 출력 조합을 지원하지 않으면 촬영을 다시 열어 서버 위치 표시로 돌아간다. 실제 안경의 동시 출력 지원·fps·발열은 설치 후 확인해야 한다.
- 가림, 불확실한 특징, 250ms 이상의 분석 프레임 단절, 최근 정체 확인의 1.8초 만료 시 추적 표시를 버린다. 늦게 도착한 웹 좌표는 현재 화면과 다시 맞춘 뒤 사용한다. 화면 각도/거리와 눈-카메라 차이는 기존 수동 HUD 보정이 적용된다.
- **안경 표시 확인**은 안경의 View가 그린 대상 ID·위치와 MediaPlayer의 표시 상태를 받아 PC에 재현한다. 대상 이름·개수, 로딩/재생 여부를 보여준다. 카메라 영상이나 눈에 겹쳐 보이는 광학 화면의 캡처가 아니다.
- 영상 `/cam/upload`·`/cam/ws`와 HUD `/recognition/device`·`/recognition/hud`는 별도 WebSocket 연결이다. 공용 HTTPS 443을 사용하며 HUD는 최대 4Hz, 연결당 미확인 메시지 1개만 허용한다. 갱신이 2.2초 끊기면 PC의 오래된 표시를 지운다. 전송·렌더링 대기는 분리되지만 무선망과 기기 자원까지 별개가 되는 것은 아니다.

검증: Node 41개 검사, JVM의 두 대상 이동·가림·만료·버튼 취소 검사, 실제 Chrome OpenCV 특징을 APK의 추적 코드로 넘기는 검사, Chrome PC/모바일 화면 검사, 별도 Cloudflare 시험 주소의 HUD 전송과 재생 상태 검사를 통과했다. `results/native-tracking-0.2.10/`에 결과를 기록했다. JVM 처리 시간은 안경에서의 처리 성능을 뜻하지 않는다. USB/ADB 기기가 연결되지 않아 실물 카메라와 안경 버튼은 아직 검증하지 못했다.

## Cloudflare 고정 제어 웹 (현재 사용)

https://glass-2412.youqlrqod.workers.dev/recognition

로컬 서버나 임시 터널 없이 기존 안경 앱이 Cloudflare로 직접 전송한다. `/server.txt`는 항상 같은 Worker 주소를 반환한다. 안경 앱 0.2.5의 기존 통신 규격(`/next`, `/stream`, `/frame`, `/tele`, `/play`)을 유지한다.

- 안경 앱을 열고 웹에서 **안경 촬영 시작**을 누른다. H.264 30·40·60fps 또는 JPEG 5fps를 선택한다.
- 안경으로 대상을 본 뒤 **등록할 화면 멈추기**를 누르고 대상 외곽을 드래그한다. 이름과 연결 영상을 선택해 새 대상을 등록한다.
- **외부 사진으로 등록**에서는 안경 연결·촬영·벡터 JSON 없이 JPG·PNG·WebP 사진만 선택해 등록할 수 있다. 새 대상 이름과 연결 영상을 지정하거나 기존 대상을 선택한 뒤 사진 여러 장을 한 번에 저장한다(대상당 최대 60장). 사진 전체를 참조로 사용하므로 물체가 크게 보이도록 배경을 줄여 준비한다. 웹에서 긴 변 최대 640px의 JPEG로 변환하며 기존 등록 이미지는 유지한다.
- 외부 사진의 중앙에만 글자·무늬가 있어도 실제 특징점 분포를 기준으로 인식한다. 사진 전용 참조를 원본·65%·45% 축척으로 준비하고, 고밀도 검색을 전체 화면과 부분 영역에 순환 배분한다. 고유 대응점 12개·RANSAC 일치점 10개·일치 비율 45% 및 공간 분포 검사는 유지한다. 작은 제목의 원근 외삽이 흔들릴 때는 일치점 오차가 허용되는 경우에만 아핀 변환을 사용한다. 벡터 JSON을 다시 등록할 필요는 없으며, 이 변경은 사진의 ORB 매칭 경로를 보완한다.
- 사진을 새로 찾으면 기하 검증을 통과한 결과를 먼저 표시하고 다음 스캔에서 다른 물체 검색을 이어간다. 성공한 참조 축척을 우선 비교하고 벡터 모델은 참조 준비 때 미리 연다. 캐시는 비교 순서만 바꾸며 매번 현재 영상으로 동일한 일치점·공간 검증을 수행한다.
- 등록이 없어도 대상 목록·등록 이미지 공간·추가 버튼이 표시된다. **이미지 추가할 대상**에서 기존 대상을 선택하거나 새 대상을 만들 수 있다. 대상 목록에서 항목을 누르면 등록 이미지가 펼쳐진다. 다른 각도에서 영역을 선택하고 **이 대상에 이미지 추가**를 누르면 같은 대상에 추가된다(대상당 최대 60장). 썸네일을 누르면 확대 미리보기와 개별 삭제가 가능하다. 기존 단일 이미지도 첫 번째 등록 이미지로 유지한다.
- 어느 등록 이미지와 일치하든 같은 대상 ID와 연결 영상으로 처리하므로, 각도가 바뀌어도 네모·이름을 중복 표시하거나 영상을 다시 시작하지 않는다.
- **인식 시작** 후 시야의 각 대상에 초록 테두리·이름을 표시한다. 중앙에 1.5초 유지하면 웹과 안경에 연결 영상을 재생한다.
- 제어 웹이 영상 해석과 OpenCV ORB 이미지 특징 비교를 수행하므로 **자동 인식 중에는 Chrome 제어 웹을 열어 둔다**. 별도의 Mac 서버는 필요 없다.
- 이미지 등록 방식이며 신경망 재학습은 아니다. 글자나 무늬가 있는 표면에 적합하다. 입체 기기의 각도·반사·조명 변화에 대한 정확도는 실제 안경 영상으로 확인해야 한다.
- 등록 이미지는 Cloudflare Durable Object의 SQLite에 보관한다. 촬영 영상은 실시간 전달용 짧은 버퍼만 유지하며 전체 녹화 저장은 하지 않는다. 현재 단일 시험 공간이며 모든 연결 안경에 같은 재생 명령을 보낸다.

### 안경 가이드와 영상 등록 (0.2.9)

1. 안경에 `glass-video-0.2.9.apk`를 한 번 설치한다. 이후 가이드 조정은 웹에서 한다. 촬영·H.264 전송 설정은 0.2.8과 같다.
2. 대상 목록에서 기존 대상을 선택하거나 새 이름과 연결 영상을 입력한다. **안경에 가이드 켜기**를 누른다.
3. 원/네모와 안경 테두리 위치·크기를 정한다. 현재 등록 거리에서 같은 물체의 모서리를 기준으로 웹의 카메라 저장 영역을 따로 맞춘 뒤 **이 위치로 보정 저장**을 누른다. 원은 HUD 조준 가이드이며 저장 이미지는 카메라의 네모 영역이다. 보정된 카메라 중심은 이후 재생 조준 판정에도 사용한다.
4. **30초 영상 등록 시작**: 정면·좌측·우측·거리 변화로 천천히 본다. 특징점 광류와 RANSAC으로 영역을 추적한다. 흐림(라플라시안 분산 <45), 부족한 ORB 특징(<20), 비슷한 장면(32×32 명도 정규화 MAD <10)은 제외한다. 이 기준은 초기 경험값이며 실제 장면에서 조정이 필요하다. 추적을 잃거나 프레임이 600ms 이상 끊기면 자동 수집을 멈추고 **다시 잡기**를 요구한다. 배경을 의미적으로 분리하는 모델은 아니다.
5. 최대 45개 후보를 확인하고 잘못 잡힌 장면을 제외한 뒤 묶음 저장한다. 대상당 총 60장, 기존 이미지는 유지한다. JPEG와 영상 내 시각·선명도·특징 개수를 서버 SQLite에 저장한다. 전체 영상·카메라 포즈·3D 모델·ORB 기술자 자체는 저장하지 않으며 기술자는 웹 인식 엔진 준비 때 계산한다.
6. 저장 후 물체를 시야 밖으로 옮겼다가 다시 보여 주어 **다시 찾기**를 확인한다. 이 과정은 자동 재생하지 않는다. 새 특징 매칭 3회가 확인돼야 통과하며, 성공해도 다른 환경의 정확도를 보장하지 않는다. 가이드를 종료하고 인식을 시작한다.

가이드는 서버가 저장·전달하고, 영상 분석은 Chrome의 별도 Web Worker에서 실행한다. 한 번에 최신 프레임 하나만 분석해 표시 대기열에 분석 작업이 쌓이지 않는다. 전체 ORB 매칭 사이를 짧은 광류 추적으로 연결하며 마지막 특징 매칭 후 1.8초가 지나면 해당 추적을 폐기한다. 영상 재생에는 1.2초 이내의 특징 매칭도 필요해 광류 추적만으로 새 재생이 일어나지 않는다. 웹이 종료되면 가이드는 최대 약 5초 후 만료된다. 등록 중 자동 인식·재생을 막고, 다른 웹의 동시 가이드 조작을 제한한다. 물체 전체가 단색이거나 새로운 뒷면이면 추가 참조가 여전히 필요하다.

새 앱 0.2.9는 고정 서버 우선 접속, 30초마다 주소 재확인, 초록색 조준 표시를 포함한다. 다운로드: https://glass-2412.youqlrqod.workers.dev/downloads/glass-video.apk
이 앱 변경에는 한 번 설치가 필요하다. 이후 등록 이미지·영상 목록·인식 로직·재생 조건은 웹 배포로 변경한다. APK 자체를 무인 설치하는 자동 업데이트는 구현하지 않았다. 안경 HUD와 카메라 영역을 웹에서 따로 보정할 수 있다. 현재 거리의 수동 보정이며 모든 거리에서 일치하는 공간 AR은 아니다.

0.2.8은 원본의 Camera2 해상도·고정 fps 선택·하드웨어 H.264 설정(2Mbps, 키프레임 1초)을 유지한다. Cloudflare의 `transport: websocket` 명령을 받으면 같은 인코더 출력을 100ms 단위로 지속 연결에 보낸다. 이전 로컬 서버 명령에는 기존 순차 HTTP POST 전송을 그대로 사용한다. 신규 전송은 밀렸을 때 연결을 반복해서 끊지 않고 전송 대기열을 제한하며 다음 키프레임부터 복구한다. 재연결마다 SPS/PPS를 다시 보낸다.

서버→웹 영상은 기본적으로 단일 HTTP 응답 스트림(`/cam/live`)으로 전달한다. 프레임마다 ACK를 기다리던 WebSocket 전달 창에서 참조 프레임이 누락되던 병목을 우회한다. 안경→서버의 지속 WebSocket 연결과 APK 0.2.8은 그대로 사용한다. 비교용 이전 웹 수신 경로는 `?media=websocket`으로 선택할 수 있다. HTTP 패킷은 길이·메타데이터·원본 H.264 바이트로 구성하며, 연결 해제 시 구독을 정리하고 최신 키프레임부터 복구한다. 서버 대기열은 128KiB로 제한한다.

웹은 한 화면 갱신에 서로 다른 영상 프레임 하나를 표시한다. 고정 시작 대기는 없으며 첫 프레임부터 표시한다. 표시 대기열은 최대 200ms 분량(60fps에서 12장)이고, 브라우저에서 해석 후 200ms 넘게 기다린 프레임도 폐기한다. 이전의 250ms 시작 대기와 최대 800ms 대기열을 줄였다. 100ms 단위로 몰려오는 프레임을 고른 간격으로 보여주기 위한 짧은 큐는 유지한다. 네트워크가 크게 흔들리면 오래된 프레임을 버리므로 표시 fps가 일시적으로 낮아질 수 있다. 설정·서버 수신·웹 도착·해석·표시 fps를 각각 표시한다. 웹 fps는 2초마다 실제 처리 개수로 계산하며 서버 API 응답을 기다리지 않는다. 사진 모드와 이전 APK의 HTTP 업로드도 받을 수 있다.

촬영 설정을 SQLite에 보존하며, 앱을 다시 열면 최초 조회 다음 명령에서 촬영을 복원한다(기존 APK는 최초 조회의 명령을 무시하기 때문). 안경의 제어 연결이 살아 있으나 영상이 12초간 멈춘 경우 카메라를 최대 3회 다시 연다. 최초 연결은 30초 기다린다. `/cam/stats`에는 웹별 누락 조각·해석/표시 fps·총 프레임 개수와 서버 도착부터 표시까지의 프레임 나이를 포함한다.

`cloud/worker.mjs`가 기존 앱 API와 Durable Object를 제공하고, `cloud/app.js`가 제어 화면, `cloud/decoder.js`가 H.264 해석, `cloud/matcher.js`가 이미지 인식을 담당한다. `cloud/opencv.js`는 OpenCV 공식 4.13.0 빌드이다.

배포된 웹에서 합성 두 대상 인식 및 저장소 촬영 영상의 H.264 해석을 확인했다. 2026-11-05 실제 안경의 Cloudflare 수신은 약 60fps였지만 기존 웹 표시는 약 12fps였다. 별도 시험 Worker에 녹화 영상을 실제 APK의 Java 전송 코드로 보내는 HTTP 수신 시험에서 720p/60fps/2Mbps의 표시는 약 40fps, 500kbps에서는 약 45fps 수준이었다. 이 수치는 실물 안경의 개선 후 측정값이 아니며 안정적인 60fps 또는 지연 해결을 입증하지 않는다. 도착 공백·프레임 누락이 남아 있다. HTTP 분할 패킷·접속 정리·키프레임 복구·프레임 표시·상태 복원 등을 포함한 Node 검사 19개가 통과했다.

운영 웹에는 디코더의 구간 누락·기준 프레임 대기·초기화로 폐기된 프레임, 표시 큐 폐기 사유, 큐 깊이·대기 시간을 기존 지표 요청에 추가했다. HTTP 화면을 새로 연결할 때도 기준 프레임을 요청하며 전체 요청은 최대 초당 1회로 제한한다. H.264 디코딩 정책은 유지하며 표시 큐만 위와 같이 줄였다. 즉시 표시 시작, 30·40·60fps 재생, 짧은 화면 갱신 정지 후 최신 영상 복구를 포함한 Node 검사 25개가 통과했다.

## 이전 로컬 서버 방식 (참고)

아래는 기존 프로젝트의 서버 실행과 촬영 구성 기록이다. 현재 Cloudflare 사용에는 `node server/server.mjs` 또는 `tools/tunnel.py`를 실행하지 않는다.


AI(또는 사람)가 서버에 "a 틀어"를 보내면, 안경이 그 영상을 서버에서 받아 재생한다.
영상은 APK에 넣지 않는다(APK 12KB). 영상 추가는 서버만 고치면 된다.

```
AI ──/play?key=a──▶ 서버 ──(/next 답)──▶ 안경 앱 ──/v/whale.mp4──▶ 재생
```

## 서버
```
node server/server.mjs                       # http://localhost:8787 (테스트 페이지에 키별 버튼)
cloudflared tunnel --url http://localhost:8787   # 외부 주소(https://xxx.trycloudflare.com)
```
- 영상 목록: `server/videos.json` (`"a": {"title": "...", "file": "whale.mp4", "loop": false}`), 파일은 `server/videos/`
- AI가 부를 주소: `GET /play?key=a`, `GET /stop`. `TOKEN=비밀값`으로 켜면 `&token=비밀값` 필요
- 안경 신호는 롱 폴링(`/next`, 최대 25초 대기). SSE는 Cloudflare 빠른 터널이 붙잡아서 안 씀

### 2026-11-06 전달 경로의 누적 지연 수정

실제 연결된 0.2.9 안경을 같은 Mac에서 동시에 받아 비교했을 때 45초 동안 HTTP 2,359장 수신 / 987장 표시, 기존 JSON WebSocket 2,079장 수신 / 1,718장 표시였다. 당시 인식은 꺼져 있었고 표시 대기열 손실이 대부분이었다. HTTP에서 데이터가 한꺼번에 도착하는 구간이 관찰됐다. 기존 200ms 표시 큐 제한은 그 이전의 네트워크 대기열을 제한하지 못했다.

- 웹 기본 경로를 바이너리 WebSocket(`/cam/ws?binary=1`)으로 변경했다. HTTP는 `?media=http`로 비교할 수 있다. 안경의 Camera2/H.264 업로드와 APK는 변경하지 않았다.
- WebSocket의 최근 ACK 왕복 시간에 따라 전달 창을 16~32개 패킷으로 제한한다. 기존 JSON WebSocket 클라이언트의 경로도 유지한다.
- 서버 ping/pong과 브라우저 단조 시계로 시계 차이·왕복 불확실성을 구한다. 화면 표시에는 서버 수신 이후 추정 나이를 사용한다. 클라이언트 벽시계의 시간 차이를 실제 지연으로 간주하지 않는다.
- 짧은 영상 전달 지연은 H.264 참조 프레임을 유지하며 해석한다. 서버 수신 이후 나이의 하한이 700ms를 넘는 화면은 표시하지 않는다. 1.8초 이상 밀린 인코딩 패킷은 버리고 최신 키프레임을 요청한다. 최신 패킷으로 회복되지 않으면 이전 연결의 종료 응답을 기다리지 않고 새 연결을 만든다. 서버에 촬영 영상 자체가 들어오지 않는 동안에는 이 감시로 재접속을 반복하지 않는다.
- 이 제한은 카메라 촬영부터 화면 표시까지 700ms를 보장하지 않는다. 안경→서버 지연은 제외되며 clockUncertaintyMs를 함께 봐야 한다. 늦은 프레임을 버리므로 네트워크가 불안정하면 표시 fps는 낮아질 수 있다. 일정한 60fps를 달성했다고 주장하지 않는다.
- 34개 Node 검사 통과. 저장된 기존 대상의 8개 이미지는 배포 전후 동일함을 확인했다. 별도 재전송 시험에서는 최신 화면 복귀가 확인됐지만 표시 fps 변동이 남았다. 실물 안경의 변경 후 검증은 연결 재개가 필요하다.

추가로 WebSocket 종료 이벤트의 예약 코드 1005/1006을 종료 프레임에 그대로 보내던 문제를 수정했다. 시험 Worker에서 상태 코드 없이 닫은 연결은 정상 코드 1000으로 약 363ms 후 종료됐다. 이후 재전송 복검에서는 낮은 표시 fps와 재연결이 남았고, 500kbps 추가 시험은 Mac의 `getaddrinfo ENOTFOUND`로 중단됐다. 이를 성공한 성능 검사로 집계하지 않는다. 운영 최종 버전은 `ea1c3a03-ec5d-4f61-9578-011f68ffb6ad`이며, 사용자가 지금 안경을 켜기 어렵다고 답해 실제 장치 검증은 다음 연결 때 진행한다.

최종 후속 HTTP 확인도 Mac에서 10초 응답 제한에 걸렸다. 배포 명령의 성공과 앞선 기능 검사는 확인됐지만, 이 시간대의 실제 연결 안정성·60fps 회복은 미확인이다. 실패 로그도 `results/pipeline-validation-20261106/binary-replay-*.log`에 남겼다.

### 2026-11-06 새 화면이 나오지 않는 연결의 복구

후속 실물 표본에서 웹 수신·해석 약 35fps, 표시 약 12fps가 관찰됐다. 누적 프레임 손실에는 탭이 숨겨졌던 시간도 포함되어 있으므로 전체 손실을 네트워크 문제로 계산하지 않는다. 실물 촬영은 비교 시작 전에 종료됐다. 별도 Cloudflare 서버로 녹화 H.264를 전송한 시험에서는 표시 루프의 RAF 간격이 약 16.7ms로 일정해도 데이터가 몰려 도착했다. 같은 디코더 출력을 세 표시 정책으로 비교했으며, 큐를 늘리는 변경은 개선이 거의 없었고 서버 나이 제한을 없애면 수 초 늦은 화면을 재생했다. 이 시험은 표시 정책 비교를 위해 앱의 자동 재연결을 실행하지 않으므로 운영 앱 전체의 평균 fps와 동일시하지 않는다.

화면 표시 제한(700ms + 시계 불확실성)과 인코딩 패킷 폐기 제한(1.8초 + 불확실성) 사이에 들어온 영상은 모두 표시에서 제외되면서도 수신 감시를 계속 갱신했다. 이를 수정해 화면을 실제 표시한 시간을 따로 감시한다. 보이는 활성 페이지에서 영상은 도착하지만 1.2초 동안 새 화면이 없으면 복구하며, 30초 안에 두 번 반복된 WebSocket 연결은 같은 Cloudflare 서버의 HTTP 수신으로 전환한다. 전환은 한 방향으로 유지하고 `?media=ws` 또는 `?media=http`로 고정한 비교 세션은 존중한다. HTTP 중단 뒤 이전 요청의 완료 콜백이 중복 연결을 만들지 않도록 소유권 검사도 추가했다. 숨겨진 탭으로 돌아오면 최신 연결을 열며, 등록용으로 멈춰 둔 이미지는 보존한다.

37개 Node 검사와 실제 H.264 바이트를 Chrome에서 해석하는 통제 시험을 통과했다. 통제 시험은 1.3초 지연된 패킷이 계속 들어와도 화면 멈춤을 감지하고 WebSocket 두 번 후 HTTP 하나로 전환하는지, 탭 복귀 후에도 동시 HTTP 연결이 하나인지 검사한다. 정상 패킷으로 전환한 뒤 약 60fps가 표시됐지만 이 수치는 모사한 네트워크에서의 회귀 검사이며, 실물 안경이나 실제 인터넷의 성능 보장이 아니다. APK와 카메라 촬영 설정은 변경하지 않았다.
