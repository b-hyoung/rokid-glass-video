# 구조 개선 및 정식 배포 구현 계획 — 2026-11-09

기준: ZNTKS / 8937a26, 앱 0.2.19, region-v14-fast-photo, 기존 자동 검사 77개.

이 문서는 구현 계획이다. 아래 구조 변경·알고리즘 변경·버전 번호·성능 목표는 아직 적용되거나 달성된 결과가 아니다.

## 1. 첫 정식 버전의 범위

- PC와 안경을 같은 Wi-Fi에서 함께 사용한다. 운용 단위는 제어 PC 한 대와 안경 한 대다.
- 로컬과 Cloudflare에서 동일한 인식 엔진·판정 규칙을 사용한다. 연결·저장 어댑터만 구분한다.
- 기존 사진·벡터 등록, 여러 대상의 표시, 2.5초 조준 재생, 버튼 종료, 짧은 추적 유지, 파일 테스트와 실물 세션 분리를 유지한다.
- 등록한 물체의 수·종류·배치를 고정하지 않는다. 기존 세 물체의 배치에만 맞춘 규칙을 만들지 않는다.
- 안경 단독 인식, 임의 외부망 연결, 복수 안경 동시 제어는 이번 첫 정식 버전의 보장 범위에 포함하지 않는다. 여러 운용 단위가 같은 클라우드를 사용할 때는 권한과 데이터를 분리한다.

## 2. 변경 원칙과 검증 기준선

한 커밋에 구조 이동, 통신 정책 변경, 인식 기준 변경을 섞지 않는다. 각 단계는 독립적으로 검증하고 되돌릴 수 있게 만든다. 운영 데이터와 서명 키를 보존하고, 이미 성공하는 사진 인식·재생 제어를 회귀 기준으로 삼는다.

현재 기준 기록:

- 화면 사진 첫 처리: 5회 평균 64.3ms. 카메라 촬영·인터넷 왕복을 제외한 PC 엔진 재현값이다.
- 로컬 UI 첫 표시: 사진 94ms / 녹화 영역 선택 127ms의 표본이 있다. 위 엔진 처리 시간과 같은 지표가 아니다.
- 물체: 자동차 약 0.4~1.3초, 가방 약 0.8초 또는 미탐지, VR 약 3.3초 또는 미탐지. 정확히 지정한 세 물체 영역의 분류만 수행하면 약 59.5ms였다.
- 과거 36/36 표시는 '어떤 대상이라도 표시된 프레임 수'다. 세 물체가 각각 36/36 인식됐다는 의미로 사용하지 않는다.

먼저 동일한 등록 정보·동일한 입력·동일한 PC 조건의 재현 패키지를 만든다. 현재 임시 폴더에 있는 검사 스크립트에 의존하지 않도록 실행기를 저장소에 넣고, 필요한 입력 파일과 모델은 해시로 고정한다. 사용자 원본 영상 전체·서명 키·운영 데이터베이스는 테스트 소스에 넣지 않는다.

측정 항목:

1. 대상별 첫 인식 처리 시간과 실제 첫 표시 시간. cold/warm을 나눠 중앙값·P95·미탐지 수를 기록한다.
2. 대상별 표시 유지율, ID 변경, 박스 위치 오차, 진행률 중단·재개, 잘못된 자동 재생.
3. 초당 요청·메시지, DB 읽기, 재연결, 활성 스레드 수, CPU·메모리.
4. 안경의 실제 표시·버튼 취소·발열·배터리. PC 처리 시간을 실물 촬영→표시 시간으로 대신하지 않는다.

## 4. 실행 단계

### 단계 0 — 재현 가능한 기준선과 배포 보호 장치

작업:

- 위 측정 항목을 수집하는 단일 검사 명령과 대상별 정답 정보를 준비한다.
- 빌드·로컬 실행이 요구하는 모델, ORT 파일, 동영상 목록, 앱 정보를 manifest로 정의한다.
- 배포용 빌드와 웹 개발용 빌드를 구분한다. 배포용은 필수 파일 누락 시 실패시킨다.
- 기존 등록 데이터·보정값의 백업과 별도 환경 복원 검사를 준비한다.
- Node·Python·JDK·SDK·Wrangler·ORT의 실제 검증 버전을 고정한다. 임시 npm 캐시에서 임의 버전을 고르는 동작을 없앤다.

통과 조건:

- 기존 77개 검사 통과.
- 깨끗한 소스에서 필수 자산을 준비하고 인식 엔진을 시작할 수 있다.
- 모델/WASM/APK를 일부러 누락한 배포 빌드는 실패한다.
- 백업 복원 후 대상 ID, 이름, 연결 영상, 사진·벡터·보정값이 일치한다.

### 단계 1 — 동작을 유지하는 구조 분리

작업:

- cloud/worker.mjs의 카메라·WebRTC 중계, 대상 관리, 인식 상태, 재생, HUD 경로를 도메인별 핸들러로 나눈다. 상태 소유자는 하나로 유지한다.
- 메시지 검증과 재생 결정 함수를 분리해 HTTP와 WebSocket이 같은 검증 코드를 호출하도록 한다.
- TargetStore의 대상별·이미지별 반복 쿼리는 JOIN/집계 및 변경 버전별 메타데이터 캐시로 줄인다.
- 프런트 API·연결·환경 설정을 공통 클라이언트로 묶는다. local 실행기가 HTML/JS 문구를 치환하는 대신 실행 모드 설정을 전달한다.
- Android는 연결, 촬영, 재생, HUD의 소유자를 분리하되 이 단계에서는 통신 주기·판정 규칙을 바꾸지 않는다.

통과 조건:

- 같은 입력의 탐지 ID·박스·진행률·재생 명령이 기준선과 같아야 한다.
- 동일 조건의 처리 시간 중앙값·P95가 기준선보다 10% 넘게 악화하면 원인을 확인하고 다음 단계로 넘기지 않는다. 이 수치는 회귀 허용 기준안이며 성능 개선 예측치가 아니다.
- 운영 등록 데이터와 로컬/파일 테스트 분리가 유지된다.

### 단계 2 — 통신 수명과 요청량 개선

작업:

- Android 작업에 세션 세대 번호와 취소 소유자를 둔다. stop 시 세대를 무효화하고 예약 작업·연결을 취소한다. 이전 HTTP 응답이나 콜백은 새 세션 화면에 적용하지 않는다.
- PC와 안경은 연결 직후 상태 스냅샷을 받고, 이후 변경 알림을 받는다. HTTP 상태 조회는 연결 실패 시의 대체 경로로 둔다.
- 안경의 실제 HUD 그리기 보고와 서버의 인식 계산 결과를 다른 메시지로 유지한다. 둘을 같은 의미로 표시하지 않는다.
- 인식 결과는 seq/epoch/at 검증을 유지한 메시지로 전송한다. 미확인 메시지와 최신 결과 수를 제한해 오래된 결과가 쌓이지 않게 한다.
- 재생·종료·촬영 명령은 상태 표시 메시지 뒤에 오래 대기하지 않도록 별도로 우선 처리하고 중복 명령 방지 규칙을 유지한다.
- 끊김·5xx·요청 한도 오류에 지수 백오프와 상한을 둔다. 초기안은 1→2→4초, 최대 30초에 작은 무작위 지연을 더한다. 비활성 탭의 불필요한 조회를 중단한다.

통과 조건:

- 앱 빠른 백그라운드/복귀 50회 후에도 역할별 활성 통신 작업은 하나다. 이전 세션 콜백이 새 상태를 덮어쓰지 않는다.
- 정상 WebRTC 연결에서 상태 확인용 HTTP 요청을 기존 측정 대비 80% 이상 줄이는 것을 검증 목표로 삼는다. 전체 요금·전체 트래픽이 같은 비율로 줄어든다고 주장하지 않는다.
- 네트워크 단절·복구, 중복 명령, 영상 로딩 중 취소, 재생 중 다른 대상 진입 검사를 통과한다.
- 첫 사진 인식과 동일 대상 진행률 유지가 퇴행하지 않는다.

### 단계 3 — 기기 연결 설정·권한·데이터 분리

작업:

- 안경 앱에 서버 선택·주소 입력·연결 상태·페어링 화면을 넣어 일반 운용에서 ADB 주소 변경을 없앤다.
- 제어 화면과 안경을 일회용 코드로 연결하고, 제어자/기기 역할의 자격 증명을 구분한다.
- 상태 조회·등록 이미지·촬영·재생·삭제·WebSocket 연결을 같은 세션 권한으로 검증한다. epoch/test 값을 인증 수단으로 쓰지 않는다.
- 기존 glasses-main 데이터는 백업 후 지정한 운용 공간으로 이관한다. 첫 이관에서 원본을 삭제하지 않고, 사진·벡터·대상 ID·보정값을 대조한다.
- 새 앱의 프로토콜/기능 협상을 넣는다. 기존 앱과의 임시 호환은 통제된 범위에서만 유지하고, 새 공개 세션에는 무인증 제어를 열지 않는다.
- 비밀 키·인증 정보는 환경 설정으로 주입하고 Git에서 제외한다.

통과 조건:

- 다른 세션의 등록 사진 조회·대상 삭제·촬영·재생·신호 중계가 거부된다.
- 서버 주소 변경 후 실제로 선택한 서버에 연결된다. control_server와 default_server의 현재 충돌을 없앤다.
- 파일 테스트가 실물 안경에 명령을 보내지 않는다.
- 데이터 이관 실패 시 기존 데이터로 복구할 수 있다.

### 단계 4 — 물체 후보 탐색과 첫 인식 개선

작업:

1. 확인된 대상 주변은 현재 프레임의 짧은 국소 검색을 우선한다. 위치 힌트는 검색 순서에만 사용하고 정체를 재검증한다.
2. 전체 장면은 낮은 해상도로 먼저 검색하고, 놓친 영역만 추가 해상도/타일로 조사한다. 흰 물체·작은 물체·화면 가장자리와 연결된 어두운 물체가 후보 생성에서 빠지는 사례를 포함한다.
3. 후보를 많이 만들었어도 한 프레임에서 전부 무제한 분류하지 않는다. 중복 후보를 합치고 시간 예산 안에서 우선순위를 배정한다. 다른 등록 대상의 탐색도 계속 돌아가게 한다.
4. 물체도 강한 벡터·참조 사진 일치와 위치 검증을 통과하면 먼저 표시하고, 무거운 전체 ORB 비교는 이후 순서로 보완하는 경로를 시험한다. 약한 증거의 시간적 재확인은 유지한다.
5. 동일 대상의 ID·진행률은 짧은 끊김을 이어가되, 다른 대상·가림 후 바뀐 물체·만료된 증거에는 넘겨주지 않는다.
6. 모든 재현에서 현재 후보 생성으로 합격 기준을 달성하지 못하면 영역 생성 부분만 교체 가능한 인터페이스로 둔 뒤 대체 검출기를 별도 비교한다. 사전 평가 없이 새 대형 모델을 기본 경로에 넣지 않는다.

초기 검증 목표안 — 현재 달성값 아님:

- 사진 첫 인식은 현재 기준선 수준을 유지한다.
- 지원 환경의 물체 첫 표시 중앙값 300ms 이하, P95 700ms 이하를 우선 목표로 측정한다. 기준을 충족하지 못하면 실패로 기록하고 모델·후보 수·시간 예산을 다시 검토한다.
- 기존 자동차·가방·VR은 두 재현 장면 모두 대상별로 탐지돼야 한다. 미탐지는 시간 통계에서 제외하지 않는다.
- 조명·거리·위치와 동시 배치를 바꾸고, 조정에 사용하지 않은 최소 두 종류의 추가 등록 물체로 검증한다.
- 배경·비슷한 물체·대상 전환 대조에서 잘못된 자동 재생이 없어야 한다. 탐지율과 오인식률을 함께 기록한다.
- 임시 '확인 중' 물체 표시는 추가하지 않는다. 재생 가능하다고 검증한 대상만 기존 방식으로 표시한다.

### 단계 5 — 정식 패키지·일반 운용 화면 정리

작업:

- 앱/웹/엔진/프로토콜/모델/필수 자산/서명 인증서 지문을 하나의 릴리스 명세에서 관리한다. 비밀 키는 명세에 포함하지 않는다.
- 앱 다운로드 링크와 표시 버전을 생성하고, 테스트 산출물과 정식 다운로드 경로를 분리한다.
- 실제 설치본의 인증서를 확인해 호환되는 배포 키와 업데이트 경로를 확정한다. 서명이 다르면 배포를 막고 전환 경로를 정한다. 기존 앱을 자동 삭제하거나 임의 키로 우회하지 않는다.
- 처음 설치하는 PC의 실행 전 점검·필수 런타임 준비·오류 안내를 제공한다. 현재 개발 PC에만 있는 파일에 의존하지 않는다.
- 일반 화면은 연결 → 대상 관리 → 인식 실행을 중심으로 정리하고 FPS·대체 전송·원시 진단은 고급 화면에 둔다.
- 이전 Node/Python 서버, 예전 recognition_local 도구, 터널 도구, 오래된 버전 안내는 legacy/examples로 분리한다. 실제 대체 경로와 재생/추적 보호 코드는 유지한다.

통과 조건:

- 깨끗한 환경에서 준비부터 빌드·인식 실행·APK 다운로드까지 재현된다.
- 실제 설치된 앱 위의 업데이트, 등록 정보·보정·영상 연결 유지가 확인된다.
- 필수 자산 누락, 잘못된 다운로드 링크, 프로토콜 불일치, 서명 불일치가 자동 검사에서 차단된다.

### 단계 6 — 출시 후보와 단계 배포

- 각 단계는 별도 커밋으로 ZNTKS에 반영한다. 로컬 검증 후 격리한 출시 후보 주소와 데이터 공간에서 검사한다.
- 출시 후보에서 같은 Wi-Fi 실제 안경으로 최소 60분 연속 운용, 앱 재진입, Wi-Fi 끊김·복구, 여러 물체, 가림·재등장, 긴 영상 재생과 버튼 종료를 확인한다.
- 원본 등록 데이터·배포 버전·모델 해시·인증서·설정 백업을 남긴다. DB 변경은 이전 버전과의 호환 여부를 따로 확인한다. 코드만 되돌려도 데이터가 복구된다고 가정하지 않는다.
- APK 호환성과 연결이 확인된 뒤 웹 기본 경로와 다운로드를 정식 버전으로 전환한다. 실물 검증 없이 자동 검사만으로 출시 완료로 처리하지 않는다.
- 운영에서 오류율·요청량·대상별 인식 지연을 확인하고 문제가 생기면 웹/서버는 검증된 이전 자산과 설정으로 복구한다. 앱은 낮은 versionCode APK를 그대로 덮어쓰는 복구를 가정하지 않고, 이전 안정 소스를 더 높은 versionCode와 같은 서명으로 재빌드하는 전방 수정 절차를 준비한다. 데이터 복구는 별도로 검증한다.

## 5. 단계별 산출물과 첫 착수 단위

| 순서 | 산출물 | 주요 효과 | APK 업데이트 |
|---|---|---|---|
| 0 | 재현 실행기·기준 기록·필수 자산 검사 | 이후 변경의 비교 기준 | 필요 없음 |
| 1 | 공통 코어/어댑터·상태 소유자 분리 | 유지보수·변경 안전성 | Android 분리 포함 시 필요 |
| 2 | 단일 통신 작업 소유자·상태 구독·백오프 | 재진입 안정성·요청량 | 필요 |
| 3 | 연결 설정·페어링·권한·데이터 이관 | 설치·운영·데이터 분리 | 필요 |
| 4 | 시간 예산이 있는 물체 영역 탐색 | 물체 첫 인식·미탐지 개선 | 기존 프로토콜 유지 시 웹 변경으로 가능 |
| 5 | 검증된 정식 패키지·일반 UI | 배포 재현성·업데이트 | 정식 서명본 설치/업데이트 |
| 6 | 실물 운용 기록·백업·롤백 자료 | 출시 판단 | 검증한 후보 기준 |

첫 구현은 단계 0과 서버/웹의 동작 보존 분리까지를 한 묶음으로 시작한다. Android 통신 변경과 인식 알고리즘 변경은 그 다음 별도 묶음으로 진행한다. 전면 재작성보다 현재 통과 동작을 보존하면서 검증 가능한 경계를 만드는 것을 우선한다.
