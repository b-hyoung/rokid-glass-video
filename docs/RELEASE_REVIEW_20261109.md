# 정식 배포 준비도 검토 — 2026-11-09

검토 기준: `8937a26` / `ZNTKS`, 앱 소스 0.2.19, 인식 엔진 region-v14-fast-photo.

## 결론과 배포 범위

현재 코드는 PC와 안경을 함께 사용하는 내부 시연·개발 버전으로 활용할 수 있다. 일반 사용자에게 설치·연결·업데이트·운영을 맡기는 정식 배포는 아직 보류하는 것이 맞다. 주요 이유는 필수 배포 자산 검증 부재, APK 버전·서명 불일치, 공개 제어 API의 인증·세션 분리 부재, 통신 스레드 수명과 요청량 관리, 물체 영역 탐지의 미완성이다.

이번 검토는 실행 코드를 수정하거나 배포하지 않았다. 현재 프로젝트의 dist, 로컬 데이터베이스, 운영 등록 데이터를 변경하지 않았으며 깨끗한 빌드 검사는 별도 임시 폴더에서 수행했다. 앱스토어 제출 심사 판정이 아닌 직접 APK·웹 배포와 운영 품질에 대한 검토다.

## 직접 확인한 근거

1. Git HEAD를 별도 폴더로 내보내 `node --test tests/*.test.mjs`를 실행: 77개 통과.
2. 같은 깨끗한 소스에서 `python tools/build_pages.py` 실행: 성공, 약 31.4MB 생성. 그러나 ONNX 모델, ORT JavaScript·WASM, 다운로드 APK가 모두 없었다. 이 파일들은 개발 PC의 build에만 있고 Git에서 제외돼 있다.
3. AndroidManifest는 0.2.19 / versionCode 21, 웹 다운로드 링크는 0.2.10 고정. 현재 PC의 0.2.19 APK는 `-tracking-test.apk`이고 빌드 도구가 기대하는 `glass-video-0.2.19.apk`는 없다.
4. 보관 APK의 JAR 서명 인증서를 keytool로 읽어 비교: 0.2.10과 0.2.19 tracking-test의 SHA-256이 다르다. 실제 설치된 기기의 인증서 및 v2/v3 서명 검사는 이번에 수행하지 않았다.
5. 기존 물체 재현 기록: 자동차 첫 표시 약 0.4~1.3초, 가방 약 0.8초 또는 미탐지, VR 약 3.3초 또는 미탐지. 영역을 정확히 지정한 분류는 세 물체 모두 기준을 통과했다.
6. Cloudflare 운영에서 `Exceeded allowed volume of requests in Durable Objects free tier.` 예외가 관측된 기록이 있다. 이번 검토에서 운영 장애를 다시 유발하거나 상태 변경 요청을 보내지 않았다.

## 정식 배포를 막는 항목

### R1 — 필수 자산이 빠져도 배포 빌드가 성공함 [P1, 재현 확인]

- 근거: `tools/build_pages.py:43-53`, `tools/build_pages.py:68-74`.
- 모델과 APK 존재 여부가 선택 조건이다. 깨끗한 소스 빌드에서는 `dist/cloud/appearance-v1.onnx`, `dist/cloud/ort/ort.wasm.min.js`, `dist/cloud/ort/ort-wasm-simd-threaded.wasm`, APK 파일들이 없다.
- 현재 운영 자산이 준비돼 있다는 사실과 새 환경에서 같은 결과를 만들 수 있다는 사실을 구분해야 한다.
- 개선: 릴리스 빌드의 필수 파일·모델 해시·웹/앱 버전을 manifest로 선언하고 누락 시 빌드를 실패시킨다. 모델·ORT 준비 과정을 고정하고 CI에서 다운로드 링크와 실제 인식 엔진 시작까지 검사한다. 개발용 웹만 빌드하는 모드는 명시적으로 구분한다.

### R2 — 앱 다운로드 버전과 서명·업데이트 경로가 불일치 [P1, 확인]

- 근거: `AndroidManifest.xml:4-5`, `cloud/index.html:34`, `tools/build_android.py:54-57`.
- 소스는 0.2.19인데 다운로드는 0.2.10이다. 최신 테스트 APK의 파일명도 정규 빌드 경로와 다르다.
- 보관 APK 인증서 SHA-256:
  - 0.2.10: `49e6f994990874054eb003a57f8967c03e4cb276deb22146e6999ca8fcc9df09`
  - 0.2.19 tracking-test: `9e8d112cb61c788ed6f3dfba9f78d3d7b14a13ba135df543e114c23f0081abd1`
- 현재 Android 빌드 도구는 기본 debug.keystore와 고정 비밀번호를 사용한다. 실제 정식 키 관리와 기존 설치본의 업데이트 호환성이 별도로 정해져야 한다.
- 개선: 배포 키·versionCode·지원 프로토콜을 고정하고 단일 release manifest에서 다운로드 링크와 표시 버전을 생성한다. 실제 설치본 위의 업그레이드를 확인한다. 이전 버전과 테스트 키 사용자의 전환 절차를 구분한다.
- Android의 서명·업데이트 기준: https://developer.android.com/studio/publish/app-signing#considerations

### R3 — 공개 API 인증과 기기·세션 분리가 없음 [P1, 코드 확인]

- 근거: `cloud/worker.mjs:22`, `cloud/worker.mjs:162-190`, `cloud/worker.mjs:305-320`.
- 모든 접속이 `glasses-main` 하나로 들어간다. 촬영·재생·대상 조회/삭제 경로에 사용자 인증·기기 페어링·권한 확인이 없다. test/epoch는 신선도·순서를 확인하는 값이며 인증 수단은 아니다.
- 일반 외부 배포에서는 다른 사용자의 명령·대상 데이터·카메라 세션을 공유하게 된다. 일부 상태 변경은 GET 요청으로도 실행된다.
- 개선: 설치 또는 페어링 단위 세션과 제어/안경 권한, 세션별 저장 공간을 두고 상태 변경을 인증된 요청으로 제한한다. 등록 이미지 조회·진단 정보에도 같은 범위를 적용한다. 내부 LAN 시연과 공개 인터넷 배포의 정책을 구분한다.

### R4 — 앱 재진입 때 이전 통신 스레드가 살아남을 수 있음 [P1, 정적 코드 경로 확인]

- 근거: `MainActivity.java:147-156`, `MainActivity.java:170-187`, `MainActivity.java:248-258`.
- onStart마다 next/sync/recognition/discovery 스레드를 새로 생성한다. onStop은 공유 running을 false로 바꾸지만 해당 스레드들을 보관·취소·종료 확인하지 않는다.
- 이전 HTTP 호출 또는 sleep이 끝나기 전에 앱이 다시 시작되면 running이 true로 복구된다. 이전 루프가 새 루프와 함께 계속 실행될 수 있다. playbackReporter만 별도의 isAlive 검사를 한다.
- 개선: 세션 세대 번호와 명시적인 작업 취소를 사용하고, 통신 작업의 소유자를 Activity와 분리한다. 빠른 백그라운드/복귀 반복 중 활성 루프 수가 하나인지 실물에서 검사한다.
- 이번 검토에서는 실제 Android Activity 재진입을 기기로 재현하지 않았다. 코드상 수명 경합과 누락된 취소 경로를 확인한 것이다.

### R5 — 고빈도 상태 폴링과 장애 시 재시도가 운영 용량을 소모 [P1, 코드 및 장애 이력]

- 근거: `MainActivity.java:171-187`, `cloud/app.js:146-151`.
- 안경은 상태 조회 후 180ms를 쉬고 다시 조회한다. 웹은 600ms 타이머마다 recognition/status와 status를 각각 호출한다. 여기에 인식 결과 제출과 다른 통신이 추가된다. 실제 요청 간격은 응답 시간도 포함하므로 단순 타이머 수치를 실측 QPS로 해석해서는 안 된다.
- 현재 HTTP 오류 때 충분한 지수 백오프나 요청 예산 관리가 없다. 웹 상태 폴링은 탭이 숨겨졌다고 중지되지 않는다.
- 개선: 인식 상태를 변경 이벤트 또는 기존 양방향 연결로 전달하고, 상태 API를 합치며, 비활성·장애·한도 초과 시 요청을 줄인다. HTTP 폴링은 통제된 대체 경로로 둔다. 요청량·DB 읽기량·연결 수를 측정해 배포 용량을 정한다.
- 무료 플랜의 요청 한도 및 초과 동작: https://developers.cloudflare.com/durable-objects/platform/pricing/

### R6 — 물체 탐지와 실물 장시간 검증이 미완료 [P1, 기능 재현과 검증 범위]

- 근거: `cloud/appearance-matcher.js:131`, `cloud/region-proposals.mjs:43-44`, `results/diagnosis-20261108/object-recognition-speed-audit.json`.
- 사진 종류 판별은 가능해도 자동 영역 후보가 만들어지지 않는 장면이 있다. VR·가방이 일부 장면에서 계속 빠진다. 사진 첫 처리 58~75ms 성공이 일반 물체 전체 성능을 보장하지 않는다.
- WebRTC는 브라우저와 안경 양쪽 모두 ICE 서버를 지정하지 않는다. 현재 범위는 같은 Wi-Fi의 단일 안경·단일 제어 브라우저다. 임의의 외부망 연결까지 검증된 제품으로 표시하면 안 된다.
- PC 브라우저가 인식 계산을 담당한다. 안경 단독 제품과 PC를 함께 쓰는 전시형 제품은 별도 요구다. 현재 HUD 위치 보정도 수동·거리 의존적이다.
- 개선: 지원할 물체·거리·조명·동시 개수·망 환경과 지연/오인식 목표를 명시하고 실제 기기에서 가림·재진입·복귀·긴 재생·발열·배터리를 측정한다. 후보 탐색은 개선하되 오인식 방지 조건을 단순 완화하지 않는다.

## 정리·구조 개선 대상

### 현재 실행 경로에서 분리·보관할 코드

- `server/server.mjs`, `server/cam.mjs`, `server/recognition.mjs`, `server/recognize.py`와 관련 HTML: 이전 Node/Python 서버 구현이다. 현재 진입점은 cloud/worker.mjs 또는 tools/local-worker.mjs다. 예전 인식은 1.5초 dwell을 사용해 현재 2.5초 규칙과 다르다. 기존 비교 도구와 deploy/original의 용도는 남기되 legacy 또는 examples로 분리하는 것이 좋다.
- `tools/recognition_local.py`와 `.html`: 이전 벡터 시험 도구다. 이름과 달리 HTML이 Cloudflare WebSocket 주소에 고정돼 있어 현재 Cloudflare 독립 로컬 모드와 혼동된다. 새 로컬 시험 도구와 구분해 보관한다.
- `tools/tunnel.py`: server.txt 파일을 배포하지만 현재 Worker는 server.txt 요청에 자기 origin을 반환한다. 과거 방식의 안내를 현행 실행 방법으로 사용하지 않도록 정리한다.
- `deploy/original/`, 과거 실측 도구와 결과: 개발·비교 자료로 가치가 있다. 정식 런타임에 섞지 않고 개발 영역에서 관리한다.
- 원본 제작 파일·3D 데모는 기능 범위를 정한 뒤 선택 패키지로 구분할 수 있다. 사용되지 않는다고 단정해 삭제할 근거는 이번 검토에 없다. 이 파일들을 정리한다고 인식 계산이 빨라지는 것은 아니다.

### 유지해야 할 코드

- WebRTC와 H.264/HTTP 대체 경로: 지원 망·앱 버전을 정하고 대체 정책을 검증한 뒤 축소한다.
- 프레임 신선도 검사, 짧은 추적 유지, trackId/epoch, 재생 잠금과 취소 처리, 전송량 제한: 문제 재발 방지용 핵심 동작이다.
- 로컬의 별도 PREVIEW 저장소: 녹화 시험이 실물 안경에 명령을 보내지 않도록 하는 분리다.
- 검증 결과와 회귀 검사: 정식 배포에서 오히려 자동화할 대상이다.

### 권장 경계

1. 공통 코어: 인식·추적·재생 결정과 프로토콜 검증.
2. 실행 환경: Cloudflare / 로컬 저장·연결 어댑터. 현재 LocalGlassRoom이 운영 코드를 재사용하는 방향은 유지한다.
3. UI: 일반 운용, 등록 관리, 진단·개발 도구를 구분한다.
4. 안경 앱: 연결 수명 관리, 촬영, 재생, HUD 표시를 각각 소유하는 컨트롤러를 두고 MainActivity는 화면·생명주기 연결을 담당한다.
5. 릴리스: 버전·모델·APK·프로토콜·해시를 하나의 manifest와 고정된 도구 버전으로 관리한다.

추가 개선:

- cloud/worker.mjs는 약 505줄에 카메라 세션·신호 중계·라이브러리·dwell·HUD·재생을 모두 가진다. 실제 도메인 경계별로 분리하고 기존 계약 검사를 유지한다.
- cloud/target-store.mjs의 목록 조회는 대상별 count/vector 쿼리, 이미지별 메타데이터 쿼리를 반복한다. JOIN/집계 및 변경 버전별 캐시로 줄일 수 있다. 현재 물체 인식의 주 병목은 후보 탐색·영상 분석이며, DB 정리가 곧바로 인식률을 높이는 것은 아니다.
- tools/start_local.py가 배포 HTML/JS의 문구를 문자열 치환한다. 실행 모드·API 주소·버전·다운로드 주소를 설정 데이터로 전달하면 문구 변경으로 로컬 동작이 깨지는 결합을 줄일 수 있다.
- 도구 버전 선택이 npm 임시 캐시와 수동 환경에 의존한다. 고정 dependency manifest/lock과 CI가 필요하다. 현재 Git에는 .github CI 설정이 없다.
- 앱/가이드 도움말의 0.2.9, 웹 다운로드의 0.2.10, 앱의 0.2.19와 문서가 섞여 있다. 한 버전 정보로 생성한다.
- Android SERVER/LOCAL 설정과 resolve의 control_server 우선 선택도 정리해야 한다. 현재 ADB로 pin하는 방식은 이를 피하지만 일반 사용자용 연결 설정은 충분하지 않다.

## 테스트 버전과 정식 버전의 차이

| 항목 | 현재 | 정식 배포 조건 |
|---|---|---|
| 실행 범위 | 개발자가 PC·Chrome·안경·동일 Wi-Fi를 준비 | 지원 환경 명시, 연결 안내·복구·설치 흐름 검증 |
| 인식 | 특정 사진 빠름, 일부 물체 미탐지 | 합의한 물체·거리·조명·동시 인식 기준 통과 |
| 사용자/기기 | 공통 제어 공간 | 페어링·권한·데이터 분리 또는 통제된 전시형 운영 |
| 배포 | 개발 PC 자산과 수동 단계에 의존 | 깨끗한 환경에서 재현, 누락 시 실패, 고정 산출물 |
| 업데이트 | APK 링크·테스트 파일·인증서가 혼재 | 서명·versionCode·호환 프로토콜과 기존 설치 업데이트 검증 |
